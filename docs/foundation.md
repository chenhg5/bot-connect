# 地基：一个能同时推进多个项目的 bot

> 状态：设计已定稿，实现见 [domain.md](domain.md) 与 `internal/domain`、`internal/app`。
> 原则不变（见 architecture.md）：不碰 agent loop、大脑可插拔、worker 是协议、软引导 + 硬保证。

---

## 0. 先回答最关键的问题：抽象多了，大脑还执行得动吗？

**会执行不动——如果让大脑自己去翻这些抽象。** 一个被唤醒的 agent，面对“目标、项目、任务、委托、风险、角色、
状态、承诺……”十几种对象和几十个工具，它会把时间花在“查清楚现在是什么情况”，而且每次查得都不一样。
小而快的模型尤其如此。

所以这份设计的核心不是对象模型，而是一条分工：

> **抽象属于脚手架，不属于大脑。**
> 脚手架负责记账、计算、排优先级，把一切**编译成一页简报（Briefing）**；
> 大脑每次醒来只需要回答一个问题：**“这一页上的事，我现在怎么处理？”**

就像一个好的幕僚给 CEO 准备的晨间简报：CEO 不需要知道表格怎么记的，他只需要知道
“今天有三件事要你决定，第一件最急，原因是……，建议是……，要找的人是……”。

具体落到四个保证上：

| 大脑醒来时的疑问 | 谁来回答 | 怎么回答 |
|---|---|---|
| 我为什么醒了？ | 脚手架 | 每次唤醒都带**原因**（消息、事件、定时、风险） |
| 现在最该做什么？ | 脚手架 | **议程（Agenda）**：按确定的规则算好分、排好序，标明“必须本次处理 / 今天内 / 关注” |
| 项目进展如何？ | 脚手架 | **项目卡**：进度、健康度（绿黄红）、下一个里程碑，都是算出来的，大脑只读 |
| 这件事该找谁？ | 脚手架给候选，大脑选 | **找人**：按“项目内角色 → 公司内角色 → 技能”匹配，再按状态过滤，给出带理由的候选 |
| 怎么判断、怎么说、怎么拆 | 大脑 | 这才是大脑的活：判断、沟通、拆解、取舍 |

大脑看到的概念只有几个名词、十来个**动词式**工具、一种简报格式。对象模型再复杂，也不会泄露到它面前。

## 1. 核心概念：尽量少，能合并就合并

### 1.1 五个名词

| 概念 | 是什么 | 例子 |
|---|---|---|
| **Worker（人力）** | 能调度的资源：人、agent、流程、别的 bot | 张三；cc-connect 的 Claude 会话；同事的 bot |
| **Project（项目）** | 一个有目标的容器：目标与衡量、成员与角色、工作、节奏、优先级 | “十月官网改版”（一个月）；“bot-connect 开源增长”（长期） |
| **Item（事项）** | 项目里的一件事，可以有子事项；里程碑也是一种 Item | “首页设计稿”；“M1：发 v0.1” |
| **Assignment（委托）** | 把一个 Item 交给一个 Worker 的一次约定（发出 → 接受 → 进行 → 交付 → 验收） | “请张三周三前确认设计稿” |
| **Event（事件）** | 发生过的任何事，进入收件箱，驱动唤醒 | 张三回复“接下”；CI 红了；周会时间到 |

刻意**不**作为独立名词的：

- **公司 / 组织 = 根项目**。公司层面的长期职责，就是“根项目”里的角色；这样“角色”只有一种：**某人在某个项目里担任某职责，
  在某段时间内**。你说的“公司层面负责什么、这个一个月的项目里担任什么”，自然统一。
- **目标不是独立对象**，是项目的属性（objective + 衡量指标）。长期目标就是一个长期项目。
- **风险不是大脑需要管理的对象**，是 Item / Project 上**算出来的标记**（加上大脑或人手动记的风险说明）。
- **承诺**（bot 答应的事）就是 Worker = bot 自己的 Item。
- **任务 vs 待办**不区分，都是 Item。

### 1.2 关系

```
Project（根项目 = 公司）
 ├── Members：Worker × Role × 时间段 × 职责
 ├── Project（子项目：十月官网改版，P1，10/1–10/31）
 │     ├── Members：张三 = 设计负责人（首页、视觉验收）；cc-agent = 前端实现
 │     ├── Objective：10/31 上线新首页；指标：首页转化率 2.1% → 3%
 │     ├── Items：M1 设计定稿 ─┬─ 首页设计稿 → Assignment(张三)
 │     │                      └─ 组件库梳理 → Assignment(cc-agent)
 │     ├── Cadence：每日 10:00 站会检查；周五 17:00 周复盘
 │     └── Card：项目说明（范围、决策、链接、约定）——项目的“记忆”
 └── Project（bot-connect 开源增长，长期，P2）……
```

### 1.3 Worker 的两层身份

| 层 | 内容 | 来源 | 变化频率 |
|---|---|---|---|
| **档案** | 是谁、擅长什么、怎么联系、工作时间、接不接活 | 配置 / 本人声明 | 很少变 |
| **成员身份** | 在哪个项目担任什么角色、负责什么、到什么时候 | 项目设置 | 随项目 |
| **状态** | 忙不忙、能不能联系上、最近靠不靠谱、现在找合不合适 | 观测 + 声明 + 推断（带有效期） | 随时 |
| **负载** | 跨所有项目手上有多少活 | 由委托算出 | 随时 |

跨项目的负载是多项目管理的关键：张三在两个项目里都是负责人，脚手架要能看到他总共压了多少，并在议程里提示
“张三本周超载”。

## 2. 唤醒：每次醒来，大脑拿到什么

### 2.1 唤醒原因（Trigger）

| 原因 | 例子 | 处理要求 |
|---|---|---|
| 消息 | 主人 / 同事 / 被派活的人说话 | 必须回应 |
| 事件 | 委托被接受 / 拒绝 / 还价 / 提问 / 交付；agent 任务结束 | 必须处理（验收、回答、改派） |
| 节奏 | 站会检查、周复盘、项目到期回顾 | 按节奏的模板做 |
| 规则 | 截止风险、长时间无进展、有人在等我们、负载超标 | 必须告知相关人并给选项 |

### 2.2 议程（Agenda）：脚手架算出来的“现在该做什么”

议程是所有需要 bot 注意的事的**排序清单**，确定性计算，不依赖大脑：

```
注意力分 = 项目优先级权重 × 紧急度 × 影响面 + 等待加分

  项目优先级权重：P0 = 8，P1 = 4，P2 = 2，P3 = 1（主人设定；子项继承）
  紧急度：已逾期 3；预计会延期 2.5；24 小时内到期 2；72 小时内 1.5；其他 1
  影响面：1 + 0.5 × 下游受它影响的未完成事项数（含间接依赖）；下游被牵连的信号 × 0.8，让根因排在前面
  等待加分：有人在等 bot（问题未答、交付未验收、还价未回复）：每等 1 小时 +0.5，上限 +6
```

每条议程项带：**是什么、为什么上榜（规则 + 数据）、建议动作类型、相关的人**。分三档：

- **Now**：本次唤醒必须处理（触发原因本身 + 分数最高的少数几条，有上限，避免一次醒来做太多）；
- **Today**：今天内要处理，下次唤醒再看；
- **Watch**：只需知道。

处理过的议程项必须有结果：**完成 / 已行动（等对方） / 推迟到某时 / 交给主人决定**。没有结果的会在下次唤醒原样回来，
推迟的到点回来——这保证了“不丢事”，又不会让大脑在一件事上原地打转。

### 2.3 简报（Briefing）：大脑每次看到的那一页

简报 = 唤醒原因 + 议程（Now 全文、Today 一句话、Watch 计数）+ 焦点项目卡 + 相关的人 + 主人的长期指示。
**只放和这次相关的切片**，更多信息用工具按需取。一个例子：

```
<briefing time="2026-10-14 10:00 周二" wake="节奏：十月官网改版·每日站会">

为什么醒：十月官网改版 的每日站会检查。

Now（本次必须处理，3 条）：
1. [等你验收] A12 首页设计稿 —— 张三昨天 18:40 交付（figma 链接），完成标准“含移动端、主人确认无误”。
   建议：按标准验收；需要主人确认就转给主人。                                    分 14.0
2. [预计延期] I7 组件库梳理 → cc-agent，截止 10/15 18:00；按该 worker 的历史速度预计 10/16 中午完成。
   阻塞 I9、I10。建议：确认进度；考虑砍范围（先做首页用到的组件）或加一个 worker。     分 12.0
3. [有人在等] 李四 3 小时前问“埋点方案找谁定？”                                  分 6.5
   找人候选：王五（本项目·数据负责人，可用，负载 2）> 赵六（公司·数据分析，休假至 10/18）

Today：I4 文案初稿明天到期（陈七，进行中，昨天有更新）· 本周五周复盘
Watch：bot-connect 开源增长 绿；张三本周承担 2 个项目共 5 件事（偏高）

项目卡 · 十月官网改版（P1，10/01–10/31）
  目标：10/31 上线新首页；首页转化率 2.1% → 3%
  进度：38%（计划 45%）黄 —— 落后约 2 天，主要因为 I7
  下一个里程碑：M1 设计定稿 10/16（4 项中已完成 2 项）
  成员：张三=设计负责人（首页、视觉验收）· 王五=数据负责人（埋点、指标）·
        cc-agent=前端实现 · 主人=最终拍板
  约定：对外发布需主人批准；设计以 figma 为准

主人的长期指示：延期风险当天就说；不确定的取舍给 2–3 个选项并给出推荐。
</briefing>
```

大脑读完这一页就知道：先验收、再处理延期、再回答李四（而且该推荐王五），不需要自己查任何东西。

### 2.4 大脑的输出约定

- 每条 Now 项都要用工具给出结果（验收 / 回复 / 派活 / 推迟 / 上报）；
- 回复给人的话由大脑写，结构化的变化通过工具落到状态里；
- 一次唤醒做不完的，显式推迟（附时间），而不是沉默。

## 3. 进度、健康度与风险：算出来，不靠大脑估

| 指标 | 计算 |
|---|---|
| 事项进度 | 叶子事项按预估工作量加权的完成比例；没有预估的按件数 |
| 计划进度 | 按时间线性：已过时间 / 项目总时长（或按里程碑计划） |
| 预测完成时间 | 剩余工作量 × 各执行者的历史速度系数，考虑依赖链 |
| 健康度 | 绿：预测按时、无高风险；黄：落后计划 >10% 或有中风险；红：预测延期、有高风险或关键人不可用 |
| 风险标记 | 逾期、预计延期、余量不足、无人负责、长时间无进展、阻塞过久、依赖延期、关键人超载 / 不可用 |

这些在每次唤醒前、以及每分钟的巡检中重新计算。风险首次出现或等级上升时触发唤醒；同一风险不重复打扰；
高风险无人处理一段时间后直接通知主人。

## 4. 找人：从“这件事要谁”到“现在找谁”

```
需要（事项或问题） ──► 1. 本项目内：角色职责匹配（“埋点”→ 数据负责人）
                    2. 上级项目 / 公司：角色职责匹配
                    3. 技能匹配（档案里的 skills）
                         │
                         ▼
                 过滤：不可联系、不同意接活、超出权限 → 去掉
                 排序：角色匹配度 > 是否已有上下文（续做优先原人）> 可用性 > 负载 > 历史靠谱度
                         │
                         ▼
                 候选列表（带理由），由大脑选；也可以“问主人”
```

“在什么时间面对什么事情去找谁”就是这条路径：**时间**由成员身份的起止决定，**事情**由职责匹配，**能不能找**由状态与规矩决定。

## 5. 节奏：多项目并行靠节奏，而不是靠大脑记得

每个项目有自己的节奏（由主人或大脑在立项时设定，脚手架按时唤醒）：

| 节奏 | 默认 | 做什么 |
|---|---|---|
| 站会检查 | 工作日每天一次 | 只看这个项目：有没有卡住的、该催的、该决定的；没事就静默 |
| 周复盘 | 每周一次 | 进度 vs 计划、风险、下周重点；给主人一条简报 |
| 里程碑回顾 | 里程碑到期时 | 验收里程碑、调整后续计划 |
| 收尾 | 项目结束 | 总结、沉淀经验到项目卡和 worker 记录 |

另有一个**总的晨报**（跨所有项目）：今天最重要的 3 件事、各项目健康度、需要主人决定的事。

## 6. 给大脑的工具：动词式，按场景分组

工具是“要做的事”，不是“表的增删改查”。大脑最常用的不超过十个：

| 场景 | 工具 |
|---|---|
| 看情况 | `brief`（重新拿简报，可指定项目）· `project_status` · `find_people(need, project)` |
| 推进工作 | `plan_items`（在项目里新建 / 拆解事项）· `delegate(item, worker, brief)` · `follow_up(assignment)` |
| 闭环 | `review(assignment, accept / revise)` · `answer(assignment, text)` · `defer(agenda_item, until)` |
| 沟通 | `send_message` · `reach(person, text, urgency)` · `escalate_to_owner(text, options)` |
| 维护 | `project_setup`（立项、成员角色、节奏、优先级）· `update_card(project, note)` · `note_person(worker, fact)` |

被派活的人只有一个工具：`respond(assignment, accept / decline / counter / progress / ask / deliver)`，只能动自己的。

## 7. 项目的“记忆”：项目卡

每个项目有一张持续更新的**项目卡**（小而结构化，有字数上限）：范围、关键决策（何时、为什么）、约定、重要链接、
已知坑。项目在焦点时注入简报。大脑通过 `update_card` 增量修改（不整体重写，避免细节被磨掉）。项目结束时，
可复用的经验沉淀到 worker 记录和主人的长期指示里。这就是自我迭代在项目层面的落点。

---

## 8. 存储：自己存，也可以“挂”到飞书上

默认本地存储（单文件 / SQLite）。但人类成员也需要看到看板，所以留一个**看板适配器**：项目与事项可以同步到飞书
多维表格或飞书任务（类似 OpenAI Symphony 用 Linear 当控制面）。人在看板上改状态，等同于发事件给 bot。
这一层是可选的，不影响核心模型。

## 9. 和现有代码的关系

| 保留 | 重做 | 去掉 |
|---|---|---|
| 渠道（飞书 / console）、大脑适配器、工具服务（MCP/REST/CLI）、身份与角色、审计、agent worker 运行器与模板、隔离与权限、定时（变成“节奏”的底层） | 对象模型（Project / Item / Member 取代 Goal / Task / Role）、唤醒与上下文（简报取代现在的上下文块）、工具集（动词式）| `plan` / `pm` 包里与新模型重复的部分（风险规则、跟进、触达逻辑会迁移过来）|

`workforce`（worker 协议、状态、委托生命周期）和 `reach`（触达）不变，它们正好是这套模型的底层。

## 10. 大脑分层：用最便宜、又足够可靠的那一层

原则：**能用代码算的不用模型；能用一个小判断解决的不用推理；需要推理的才交给 agent。**
每层都可插拔（不绑定具体厂商），每层的输入、提示和可用工具都不同。

| 层 | 做什么 | 典型实现 | 时延 | 输出 |
|---|---|---|---|---|
| **L0 代码** | 规则、计算、状态机、打分、权限、节奏、触达规矩 | 框架本身 | 毫秒 | 确定的结果 |
| **L1 判断** | 窄而明确的语义判断：这条消息是什么意图、在回复哪个委托、急不急、这件事该归哪个角色、需要快答还是深想 | System One 模型（如 TypeSafe Jev：noul / choice / score，带概率）；没有时退回 L2 的结构化判断或代码启发式 | 百毫秒级 | 类型化答案 + 概率 |
| **L2 快脑** | 需要说人话但不需要深想：寒暄、确认收到、回答进度（数据已算好）、登记某人的回复、简单派活 | 快模型的轻 agent（如 pi + 高速模型） | 1–4 秒 | 回复 + 少量工具调用 |
| **L3 深脑** | 需要推理：拆解与规划、可行性判断、风险应对方案、验收复杂交付、周复盘 | 完整 agent（Claude Code / Codex） | 十几秒到分钟 | 计划、决定、多个工具调用 |

### 10.1 路由：每次唤醒先决定交给哪一层

```
唤醒 ──► L0 先处理能确定的（议程打分、到期、权限、静默规则）
      ──► L1 判断（一次请求里并行问多个问题）：
            意图（闲聊 / 问进度 / 新需求 / 回复委托：接受·拒绝·还价·进度·交付·提问 / 改计划 / 审批 / 其他）
            若是回复委托：对应哪个委托（在这个人名下的未完成委托里选）
            紧急度、是否需要深想（快答 / 需要推理 / 交给主人）
      ──► 置信度够高、且属于可直接落地的意图（如“接下了，周三给”）→ L0 直接落状态，L2 写一句确认
      ──► 需要说话但不需要深想 → L2
      ──► 需要推理 → L2 先回“收到，我想一下”（秒级），同时 L3 异步处理，完成后在同一会话回复
      ──► 置信度低 → 上交下一层，不自作主张
```

节奏类唤醒（站会、周复盘）按模板直接选层：站会检查默认 L2（全绿就静默，有 Now 项才升到 L3），周复盘用 L3。

### 10.2 每层看到的上下文与提示不同

| | L1 判断 | L2 快脑 | L3 深脑 |
|---|---|---|---|
| 上下文 | 只有这次需要的状态切片（消息、说话人、他名下的委托列表、候选项） | 简报的精简版：唤醒原因 + 与说话人 / 当前事相关的 Now 项 + 最近几条对话 | 完整简报 + 焦点项目卡 + 找人候选 + 主人长期指示 |
| 提示 | 一个窄问题 + 明确的选项定义 | 人设 + 短协议：“快、准、短；不确定就说会跟进” | 人设 + 完整协议 + 场景 skill（规划、验收、风险应对、复盘） |
| 工具 | 无 | 少量：回复、登记回复、推迟、`think_more`（升到 L3） | 全部动词式工具 |
| 失败时 | 低置信度 → 上交 | 超时 / 出错 → 先发“我晚点回你” | 超时 → 推迟并告知 |

### 10.3 框架与大脑的边界（再确认）

框架就是**把我们能写成规则的东西用固定代码算出来**：优先级、进度、健康度、风险、找人候选、提醒节奏、权限、
状态转换。大脑只做三件事：**判断、沟通、拆解**。一个规则如果反复被大脑“判断”出同样的结果，就该下沉成代码；
一个代码规则如果总在边界情况出错，就该上交给 L1 / L3。这条边界会随着评测结果持续调整。

## 11. 落地顺序

1. **模型与存储**：Project（含根项目）、Member、Item、Assignment、Event；本地存储；CLI 可查可改。
2. **议程与简报 + 模拟评测环境**：打分规则、三档、简报渲染；虚拟时钟 + 脚本化的人 + 假 agent worker；
   用研发的 golden cases（见 [dev/goals.md](dev/goals.md)）验证“一页简报”能否让大脑做对，包括快模型。
3. **大脑分层**：L1 判断接口（Jev 实现 + 无 Jev 时的退路）、L2 / L3 路由、快答先行 + 深想异步。
4. **工具与协议**：动词式工具集；被派活的人 `respond`。
5. **节奏、人与触达**：站会、周复盘、晨报；提醒规矩。
6. **上线试用**：在飞书里用真实项目跑，按 [dev/goals.md](dev/goals.md) 记录研发指标。
7. **看板适配器**（飞书多维表格 / 任务），按需。

第 2 步是关键验证点：如果一页简报不能让大脑稳定地做出正确的下一步，就先改简报，而不是加概念。

## 12. 关于名字

“ceo-bot” 会让人期待它自己定战略、自己拍板，而这套设计里拍板的始终是主人，bot 做的是**把多个项目推进下去**——
更接近幕僚长 / 项目总管。“nextbot” 中性但看不出它做什么。建议先不急着改名，等第 2 步验证完“一页简报”的体验、
产品形态稳定后再定；改名本身成本不高（模块路径、二进制名、npm 包名、文档）。
