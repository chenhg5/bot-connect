# bot-connect 总纲：原则、分层与扩展点

> 这份文档定义 bot-connect **是什么、不是什么**，以及所有后续功能要遵守的边界。
> 具体实现见 [design.md](design.md)（接入层）、[framework.md](framework.md)（框架 / 配置分工）、
> [permissions.md](permissions.md)（权限）、[foundation.md](foundation.md)（产品设计）、[domain.md](domain.md)（领域设计）；方向调研见 [research/2026-10-proactive-collaborator.md](research/2026-10-proactive-collaborator.md)。

## 1. 原则

1. **不碰 agent loop。** 思考、规划、调用工具、写代码的循环属于现成 agent（Claude Code / Codex / pi / …），它们每几个月
   就变强一次，我们白拿。bot-connect 不实现、不包装、不改写任何 agent 的内部循环，也不自带 LLM 调用。
2. **我们是脚手架。** bot-connect 提供 agent 自己不持有、也不该持有的东西：跨会话的状态（目标、承诺、任务、记忆）、
   唤醒与长周期运行、worker 的组织与派活、权限与安全边界、自我迭代成果的保管、审计。
3. **大脑可插拔。** 任何 agent 都可以当大脑；换大脑不丢任何积累，因为积累都在脚手架里，不在某个 agent 的会话里。
4. **worker 是协议，不是实现。** 能接活、能回报的都可以是 worker：本地 agent 会话、agentflow 流程、人、另一个 bot-connect
   bot、第三方 bot（Dots、Muse、Grok bot、Hermes……）。不预设、不定死任何一种。
5. **渠道可插拔。** 飞书只是第一个；任何 IM / 协作工具都可以接入。
6. **软引导 + 硬保证。** 影响判断的用工具、skill、prompt、上下文（软）；必须可靠发生的事——唤醒、到期检查、权限、
   预算、状态完整性、审计——由脚手架执行（硬），**不依赖模型“记得”**。
7. **可信优先于聪明。** 主动性越强，边界越要硬：工具层权限、最小信息外发、外部结果视为数据而非指令、关键动作需批准、
   每次主动行为可归因。

## 2. 分层

```
   人（主人、同事、访客）
          │  IM / 协作工具
┌─────────▼──────────────────────────────────────────────────────────────┐
│ 渠道层   Platform 接口：飞书（SDK / lark-cli）、console、…（可插拔）        │
├────────────────────────────────────────────────────────────────────────┤
│ 脚手架（bot-connect 本体）                                               │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────────┐ │
│  │ 身份与权限 │ │  状态     │ │ 控制循环  │ │ worker   │ │ 学习成果保管   │ │
│  │ 角色/策略  │ │ 目标/承诺 │ │ 会话队列  │ │ 名册/模板 │ │ 记忆/skill    │ │
│  │ 动作档位   │ │ 任务/实验 │ │ 定时/心跳 │ │ 路由/队列 │ │ 打法本/统计   │ │
│  │ 预算/静默  │ │ 观察/日志 │ │ 事件/到期 │ │ 跟进/验收 │ │ 审批/来源     │ │
│  └──────────┘ └──────────┘ └──────────┘ └──────────┘ └──────────────┘ │
│  工具服务（MCP / REST / CLI，按回合 token 绑定会话与权限） · 审计          │
├──────────────────────────────┬─────────────────────────────────────────┤
│ 大脑（可插拔 agent）           │ worker（可插拔，统一协议）                 │
│ claudecode · codex · pi ·     │ 本地 agent 会话 · agentflow 流程 · 人 ·    │
│ command · 你注册的 adapter     │ 其他 bot-connect bot · 第三方 bot · …     │
│ ← 它们自己的 agent loop，不碰 → │ ← 它们自己怎么干活，不碰 →                 │
└──────────────────────────────┴─────────────────────────────────────────┘
```

**控制循环 ≠ agent loop。** 脚手架里有一个很薄的循环：决定**什么时候**唤醒大脑、**带着哪些状态**唤醒（新消息、任务回报、
定时、心跳、承诺到期、事件）。它是调度器 + 状态机，不需要智能，只需要可靠。“下一步做什么”永远由大脑判断。

## 3. 脚手架提供的能力

每项能力 = **硬的部分**（脚手架执行）+ **软的部分**（交给大脑的工具、skill、prompt）。

| 能力 | 硬（脚手架） | 软（给大脑） |
|---|---|---|
| worker 管理 | 名册、模板、实例上限、队列、隔离、回收、跟进与超时、人类 worker 的同意与催办上限 | 路由规则、派活写法（目标 / 背景 / 完成标准）、验收方式 |
| 目标管理 | 目标 / 实验 / 观察的存储与校验、复盘唤醒 | 复盘与实验设计的 skill、宪章（目标函数与约束） |
| 承诺与跟进 | 承诺存储、到期唤醒、未完成升级 | “答应了就登记”的协议 + 工具 |
| 唤醒与长周期 | 定时、心跳、事件源、后台会话与前台隔离、预算、静默时段 | 守望清单、静默约定 |
| 自我迭代 | 记忆 / skill / 打法本的存储、上限、来源、审批、跨大脑注入 | 复盘后提出修改；使用与反馈 |
| 权限与边界 | 角色 × worker 访问级别 × 工具层检查、动作三档（允许 / 需批准 / 禁止）、审计归因 | 何时请示的说明 |

“跨大脑注入”：skill 与记忆由脚手架持有（统一用开放格式，如 agentskills.io），每次调用时按当前大脑支持的方式注入
（system prompt、上下文文件、skill 目录、扩展），换大脑后积累仍在。

## 4. worker 协议

worker 协议要回答三件事：**它是谁**（档案），**它现在怎么样**（状态），**和它怎么打交道**（交互与任务生命周期）。
关键区分：**任务状态**属于一件活，**worker 状态**属于这个执行者本身，跨任务持续存在。一个 worker 可以“任务进行中”，
同时“额度快用完”“已经被催了两次”“今天情绪不好”。

### 4.1 档案（Profile）：相对稳定，声明为主

| 字段 | 含义 | 例子 |
|---|---|---|
| kind | 实现类型 | `agent_session` / `agentflow` / `human` / `bot` / `a2a` / `command` |
| principal | 它听谁的 | 我们的主人（自己的 agent）/ 它自己（人）/ 它的主人（别人的 bot） |
| skills / description | 擅长什么 | “cc-connect 仓库开发”“视频拍摄”“法务审阅” |
| trust | 我们能否约束它 | `controlled`（我们起进程、加沙箱）/ `external`（只能约束发出去什么、收回来什么） |
| interaction | 它支持什么 | 能否延续上下文、能否反问、能否拒绝 / 还价、能否报告进度 |
| channel | 怎么联系 | 本地 CLI / agentflow / 飞书私信 / A2A 端点 / webhook |
| norms | 打交道的规矩 | 工作时间、时区、首选方式（卡片 / 文字）、催办上限、接受谁派的活（consent） |
| cost model | 用它的代价 | token / 金钱 / 时间 / **社交成本** |

### 4.2 状态（State）：会变的，分维度而不是一个枚举

“busy / idle”只是其中一个维度。worker 状态由几个**正交维度**组成，展示时再派生出一个一句话的概要
（例如“忙，排队 2 个，预计 40 分钟后空出”“下班了，明早 10 点后”“今天被拒过一次，先别找他”）。

| 维度 | 回答的问题 | agent 会话 | 人 | 别的 bot |
|---|---|---|---|---|
| **可达性 presence** | 现在能联系上吗 | 进程 / 模型提供方是否可用、额度是否用尽、是否限流 | 在线 / 离开 / 勿扰 / 休假 / 下班 | 端点是否可达 |
| **负载 load** | 手上有多少活、何时能接新活 | 运行中任务、队列长度、实例上限 | 我们派的未完成活 + 自报的忙碌程度 | 对方回报的队列 |
| **健康 health** | 最近干得顺不顺 | 近期失败率、超时、认证过期、会话损坏 | —（不适用） | 近期失败、拒绝率 |
| **上下文 context** | 它已经知道什么 | 会话里做过什么、最近主题、所在分支 | 最近和它聊过 / 交给过它的事 | 同左 |
| **能力记录 record** | 交给它靠不靠谱 | 按任务类型的成功率、耗时、返工次数 | 按时率、交付质量、平均响应时间 | 同左 |
| **意愿 receptiveness** | 现在找它合不合适 | —（不适用） | 今天已打扰次数、最近是否拒绝 / 拖延、明确表达的状态（“这周很忙”）、语气信号 | 对方的拒绝 / 限额信号 |
| **授权 consent** | 它答应接什么 | 由我们配置 | 同意接哪类活、谁派的、到什么时候 | 对方主人的授权范围 |

“情绪”放在**意愿**这个维度里，而且刻意不叫“情绪”：框架关心的不是诊断一个人的心情，而是**“现在找他合不合适、
他大概率会不会接、催他会不会伤关系”**。

### 4.3 状态从哪来：声明、观测、推断

每个状态值都带来源、置信度、更新时间和有效期：

```json
{ "dim": "receptiveness", "value": "low", "source": "inferred",
  "evidence": "拒绝了 t12；今天已催 2 次；回复说“这周排满了”",
  "confidence": 0.6, "at": "2026-10-10T15:20", "expires": "2026-10-11T09:00" }
```

| 来源 | 例子 | 可信度 | 规则 |
|---|---|---|---|
| **声明 declared** | 对方说“我在休假到周五”，配置里的工作时间，A2A agent card | 高 | 优先采用；到期失效 |
| **观测 observed** | 队列长度、失败率、响应耗时、飞书在线状态 / 日历（有权限时） | 高 | 脚手架自动维护 |
| **推断 inferred** | 大脑从对话里判断“他似乎压力很大” | 低 | 只做软参考；**短期自动衰减**；不进长期记忆；不对外透露 |

对人的推断状态是个人数据，必须守规矩：

1. 只记**与协作相关**的（能否接活、时机、偏好），不给人贴性格 / 心理标签；
2. 推断值短期过期（默认一天内），不能沉淀为对某人的长期判断；
3. 只对主人可见，绝不出现在发给第三方的内容里；
4. 当事人可以问“你的 bot 记了我什么”并更正 / 清除（透明、可争辩）。

### 4.4 交互：从“下命令”到“发请求”

对可控 agent，派活就是执行；对人和别的 bot，派活是**请求**，对方可以拒绝或还价。协议按后者设计，前者只是
“总是立即接受”的特例：

| 消息 | 方向 | 说明 |
|---|---|---|
| `describe` / `status` | 脚手架 ← worker | 档案与当前状态（拉取，或 worker 主动推送变化） |
| `offer(task)` | → worker | 目标、背景、完成标准、截止、证据要求；只带最小必要信息 |
| `accept` / `decline(reason)` / `counter(deadline, scope)` | ← worker | 还价：晚一点 / 只做一部分 / 换个方式 |
| `progress(note, eta)` | ← worker | 可选；人通常靠我们按约定时间询问 |
| `input_required(question)` / `answer` | ↔ | worker 反问；bot 自己能答就答，否则问请求方 |
| `deliver(result, evidence)` | ← worker | 交付，**不等于完成** |
| `verify(accept / revise)` | → worker | 请求方验收；返工计入能力记录 |
| `cancel` / `release` | ↔ | 取消，或 worker 退回（做不了了） |
| `feedback` | → 脚手架 | 对这次合作的评价，更新能力记录 |

### 4.5 任务生命周期

```
            ┌──── declined ────┐
offered ────┼──── countered ───┼──► (bot 决定：接受还价 / 换人 / 问主人)
            └──► accepted ──► working ◄──► blocked(input_required | waiting_external)
                                 │  └──► paused（对方暂停 / 离线）
                                 ▼
                             delivered ──► verified（完成）
                                 │     └──► revising ──► delivered …
                                 ▼
                    failed / cancelled / released / expired
```

状态名与 A2A 任务状态（submitted / working / input-required / completed / canceled / failed / rejected …）一一可映射，
便于和实现了 A2A 的 agent 互通。

### 4.6 状态怎么用：路由与跟进

大脑派活时看到的是每个候选 worker 的**一句话状态 + 关键维度**，由大脑判断（软）；脚手架只执行硬规则：

| 硬规则（脚手架拦截） | 软判断（大脑参考） |
|---|---|
| 不可达 / 无授权 / 超出实例上限 → 不能派 | 适合度：技能、是否已有上下文（续活优先交给原 worker） |
| 人的静默时段、每日打扰上限、催办间隔 | 预计耗时 = 排队 + 典型耗时 |
| external worker 只能收到最小必要信息 | 可靠度：能力记录 |
| 对外派活按动作档位审批 | 代价：token / 金钱 / 社交成本、对方当前意愿 |

跟进也随 worker 类型不同：agent 超时就判失败或重试；人到点是**温和提醒**，再到点**升级给主人**而不是一直催；
别的 bot 按对方声明的节奏查询。

### 4.7 实现（不定死，持续增加）

| 实现 | 传输 | 信任 | 状态 |
|---|---|---|---|
| 本地 agent 会话（Claude Code / Codex） | 本地 CLI，会话恢复 | controlled（沙箱、访问级别、隔离） | ✅ 已有（含模板、per-user 实例） |
| agentflow 流程 | agentflow CLI；human 节点由 bot 在 IM 里问人 | controlled | 规划 |
| 人（主人、同事、外部协作者） | IM 私信 / 卡片 | external（尊重拒绝、催办上限、最小信息） | 规划（先从主人自己开始） |
| 另一个 bot-connect bot | IM 或 bot 间协议（A2A） | external（对方有自己的主人和权限） | 规划 |
| 第三方 bot（Dots / Muse / Grok bot / Hermes …） | 它们开放的 API / A2A / IM 渠道 | external | 规划，按对方开放程度逐个接入 |
| 通用 command / HTTP | 自定义命令或 webhook | 视配置 | 规划 |

### 4.8 对称性：bot 自己也是 worker

bot-connect 的 bot 对外实现同一个协议：同事的 bot、别人的 Dots，都可以把你的 bot 当 worker 派活，你的 bot 再按自己的权限、
名册和主人的规则决定接不接、交给谁做。这样“一人一个 bot”自然长成一张**人与 bot 混合的协作网络**，而不需要中心化平台。

## 5. 信任边界

| 方向 | controlled worker | external worker（人、其他 bot） |
|---|---|---|
| 我们发出去的 | 指令 + 必要上下文 | **最小必要信息**；不泄露主人的其他工作；对外动作按动作档位审批 |
| 它能做的 | 由访问级别、沙箱、deny 规则硬性限制 | 我们无法限制，只能选择交给谁、交什么 |
| 收回来的 | 结果 + 证据 | **一律视为数据而非指令**（防注入）；关键结论需证据；进入记忆前标来源、需更高门槛 |
| 身份 | 我们创建的进程 | 需认证（渠道身份、协议凭证）；名册里登记，主人授权 |

大脑本身也受同样的约束：它看到的世界（会话、worker、文件）由工具白名单决定，它能做的事由回合 token 的权限决定，
与它是哪个 agent 无关。

## 6. 不做什么

- 不实现或包装 agent loop，不自带模型调用、提示链、规划器。
- 不预设 worker 必须是 agent；不把某个厂商的 agent 写死成唯一执行者。
- 不做通用工作流引擎（那是 agentflow 的事；bot-connect 把它当一种 worker）。
- 不替大脑做判断：脚手架只决定“何时唤醒、带什么状态、什么不允许”，不决定“下一步做什么”。
- 不把记忆和 skill 锁进某个 agent 的私有格式。

## 7. 当前实现与总纲的差距

| 总纲 | 现在 | 下一步 |
|---|---|---|
| worker 协议 | `worker.Runner.Run(ctx, spec, session, prompt)`：同步、只有 agent 会话；状态只有 busy / idle + 队列 | 档案 + 多维状态（带来源 / 置信度 / 有效期）+ offer / accept / deliver / verify 交互；现有 claude / codex 作为“总是立即接受”的第一个实现 |
| input_required | 无，worker 只能猜或卡住 | worker 反问 → bot 问人 → 回传 |
| 人类 worker | 无 | 名册 + IM 派活 + 跟进；先支持主人自己 |
| 状态层 | 任务、worker、定时任务 | 承诺、目标、实验、观察 |
| 控制循环 | 会话队列、定时任务、任务回报 | 心跳 / 事件源、承诺到期、后台会话隔离 |
| 学习保管 | 无 | 有界记忆 + skill 目录 + 审批，跨大脑注入 |
| 动作档位 | 角色 × 访问级别 | 允许 / 需批准 / 禁止 + 飞书卡片审批 |
| 对外暴露 | 无 | bot 作为 worker（A2A 或 IM） |
