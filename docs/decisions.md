# Brain 的决策能力：怎么来，怎么评

> 用词：bot（brain）是 principal，负责推动一切；给它目标的人叫**委托人**（principal）。

> 结论先行：不训练模型。决策能力由三样东西组合出来：
> **(1) 规划协议**（skill + prompt，告诉它“好的 PM 怎么想”），
> **(2) 计划是一等数据**（工具强制结构：分解、依赖、并行、谁做、为什么是这个人），
> **(3) 委托人的风格配置**（风险偏好、预算、要不要先问）。
> 评估用 golden case + Jev 打分 rubric，以及上线后的结果指标。

## 1. 用两个真实问题检验当前设计

### 例 A：「帮我给我的开源项目搭建一套完整的可行的周期发版策略」

bot 是这件事的 principal：它负责把事推到底，委托人只在需要他的地方出现。
它不自己读代码、写策略，第一反应是“拆成哪几块、每块让谁做”，而且这张图只是**草案**：

| 节点 | 做什么 | 谁 | 依赖 |
|---|---|---|---|
| R1 现状调研 | 读仓库：提交频率、tag 历史、CI、贡献者数、issue 节奏 | agent（研究型） | — |
| R2 同类调研 | 3–5 个同体量项目的发版策略（semver、train、LTS） | agent（研究型） | — |
| D1 方案草案 | 基于 R1+R2 出 2–3 个方案，每个写清代价 | agent | R1, R2 |
| C1 对齐 | 和委托人、核心维护者确认：节奏、谁来发、要不要 LTS | 人（decision） | D1 |
| …… | 落地节点在 C1 之后才定，不预先编 | 待定 | C1 |

要点：
- R1、R2 **并行**；只有 C1 需要人，且只问人能回答的那一步。
- **计划在确认前不是计划**。节点、执行者、时间都要和对应的人确认（他们接下 = 节点定下），
  确认后 bot 再展开落地部分。落地怎么做取决于选的方案，提前写成“合并某个 PR”是在替人做决定。
- 如果发版是周期性的，确认后的计划里应有一个复利节点：把发版做成可复用的 worker/skill。
- 当前设计能表达这些：Item + depends_on + needs(decision) + delegate。**缺的是**：计划的状态
  （草案 → 确认中 → 已定 → 执行中），以及 brain 不一定会这样想（会自己直接写策略）。

### 例 B：「在一年内帮助我赚到 100 万」

这是**目标**，不是任务。好的 PM 先做可行性，不先做承诺：

1. **澄清约束**（问委托人，一次问完）：起始资源（钱、时间、技能、已有产品/受众）、风险底线（能亏多少）、
   不做什么（法律、道德、时间边界）。这一步是 decision/knowledge，必须找人。
2. **并行调研**（全部派 agent）：3–5 条路径（产品化现有项目、咨询/服务、内容、投资…），
   每条给出：单位经济、到 100 万需要的量、前 3 个月的验证指标、主要风险。
3. **可行性门**：汇总成“哪条路径在约束下可能、概率大约多少、要先验证什么”。
   如果都不可行，**直接说不可行**，并给出可行的降级目标（例如“一年 30 万，路径 X”）。
4. **只为第一个验证周期建项目**（例如 6 周验证路径 X 的付费意愿），设里程碑和止损条件；
   一年目标挂在根上，每个周期复盘再决定下一个周期。

当前设计缺的东西：
- **目标（Goal）与项目的区别**：目标有可行性状态（未评估 / 可行 / 有条件可行 / 不可行）、
  假设、止损条件，下面挂多个验证周期（项目）。
- **调研节点的产出是“结论 + 证据 + 置信度”**，不是代码。
- **风险偏好决定路径选择**：同样的调研，谨慎的委托人选低方差路径，激进的委托人接受高方差。

## 2. 偏好不靠模型“性格”，靠委托人配置

风险偏好是**委托人的**，不是 bot 的。它应该是配置 + 可在对话里修改的 profile：

```toml
[principal.style]
risk = "cautious"          # cautious | balanced | bold
ask_before = ["spend>500", "public", "external_contact", "irreversible"]
budget_month = 2000        # 能花的钱（API、外包、服务）
parallel = 4               # 同时在跑的 agent 任务上限
explore_ratio = 0.2        # 多少精力给“复利投资”（工具、训练 worker）
```

用法分两层：
- **规则层（代码）**：ask_before、预算、并发上限是硬约束，authorize/delegate 里检查。
- **判断层（brain）**：risk 写进 briefing，比如“委托人偏谨慎：先验证再投入；优先低方差路径；
  不确定时先问”。brain 在给方案时必须说清每个方案的风险，然后按风格推荐。

## 3. 让 brain 有这种思路：harness，不是训练

模型本身已经会分解问题，缺的是**被逼着按 PM 的方式输出**。做法：

1. **plan 工具（结构强制）**：`plan_goal` / `plan_item` 一次提交一张图：节点、依赖、每个节点的执行者类型
   （agent/人）和 why、并行组、产出物、复利标记。代码校验：
   - 每个“找人”的节点必须有 why（已有）；
   - 有依赖环、无执行者、全部串行但其实可并行 → 拒绝并说明；
   - 研究/起草类节点指给人 → 提示“这类事 agent 能做”。
2. **规划 skill（思路模板）**：遇到新目标时加载，内容是 PM 的检查单：
   - 这是目标还是任务？目标先做可行性。
   - 我知道什么、不知道什么？不知道的 → 调研节点（派 agent）。
   - 哪些步骤彼此独立？→ 并行。
   - 哪一步真的需要人？只把那一步给人。
   - 这件事会重复吗？→ 加一个复利节点（工具 / skill / 专门的 worker）。
   - 最坏情况是什么，止损条件是什么？
3. **代码算能算的**：关键路径、最早完成时间、并行度、资源冲突，用已有的 Forecast/Graph 计算，
   回给 brain 作为 plan 工具的结果（“关键路径 R1→D1→H1→B1，预计 5 天；H1 是瓶颈，等你决定”）。
4. **Jev 做快判断**：新消息“是目标还是任务”“需要可行性评估吗”“这个节点 agent 能不能做”，
   用 noul/choice 先分好类，brain 只处理需要思考的部分。
5. **复利账本**：记录每类工作做了几次、每次耗时；重复 ≥3 次的工作类型自动成为信号
   （“发版做了 3 次，每次 2h，建议做成 worker”）。这是规则，代码就能算。

训练的位置：以后如果 golden case 的失败集中在“模型不会按协议想”，可以用积累的转录做偏好数据，
但这是最后一步，而且不在我们的范围（不碰 agent loop / 模型）。

## 4. 怎么评估决策能力

三层，和现有 eval 框架一致：

**(a) 结构检查（代码，确定性）**：对 plan 工具产出的图检查：
- 研究/起草节点是否都给了 agent；
- 人节点是否都只承担 why 范围内的那一步；
- 独立节点是否并行（关键路径长度 / 总工作量）；
- 目标是否先有可行性节点再有执行节点；
- 周期性工作是否有复利节点。

**(b) Rubric 评分（Jev score，对转录打分）**：每个规划 case 问 4–6 个窄问题，例如：
- “brain 是否先澄清了约束再开始执行？”
- “是否明确说出了不可行或有条件可行的部分？”
- “推荐是否符合委托人的风险偏好 `principal.style.risk`？”
- “有没有让人去做 agent 能做的事？”

**(c) 结果指标（上线后）**：计划被委托人原样接受的比例、计划变更次数、预测 vs 实际完成时间、
人被打扰次数 / 闭环交付数（北极星是每周闭环委托数）。

规划类 golden case（新增 G20+）：
- G20 开源发版策略：调研并行、决策给委托人、落地给 agent、有复利节点。
- G21 一年 100 万（谨慎）：先问约束，调研派 agent，给出可行性结论，不立刻建执行项目。
- G22 同上（激进）：同样流程，推荐路径方差更高，但仍有止损条件。
- G23 明显不可行的目标（“下周让项目 10 万 star”）：直接说不可行，给替代目标。
- G24 重复工作：第三次派同类活时，提出做成工具/worker。

## 5. 计划的生命周期：草案要和人对齐才算数

```
draft ──(拆完、代码校验通过)──▶ proposed ──(相关的人逐个确认)──▶ agreed ──▶ active ──▶ done
   ▲                                   │ 有人改时间/拒绝/提出别的方案
   └──────────────(修订)───────────────┘
```

- 节点的“确认”复用委托机制：给人的节点就是 offer，接下 = 确认，还价 = 修订输入。
- agreed 的条件由代码判断：所有人节点已接下、委托人对关键决策已答复、没有依赖环。
- 只有 agreed 的计划才进入风险检测（will_miss 等）；草案阶段不报延期。

## 6. Reflection：放在哪、谁来做

模型自己会反思，但它审自己的计划容易“自洽地错”。外部检查的价值在于**换一个角度、问具体的问题**。
不建议随机加检查点，建议按代价放：

| 时机 | 谁检查 | 检查什么 | 代价 |
|---|---|---|---|
| 每次提交计划 | 代码 | 依赖环、无执行者、可并行却串行、该给 agent 的给了人 | 0 |
| 计划从 draft → proposed | Jev（3–5 个窄问题，一次请求） | 先澄清了吗？有可行性判断吗？找人的理由成立吗？符合风险偏好吗？ | ~1s |
| 对外说“做不到 / 不可行” | Jev | 理由是否来自证据（调研结果、预测），而不是猜 | ~1s |
| Jev 低分 | brain 自己 | 把问题和分数回给 brain，让它改或说明为什么不改 | 一次 turn |
| 事后（离线） | Jev 抽样打分 | 随机抽取已完成的决策，按同一套 rubric 评分 | 不影响线上 |

随机抽样适合**评估**（离线统计决策质量，形成指标），不适合线上：线上检查应该放在代价大、
不可逆的决策点上。Jev 分数不直接否决 brain，只是把具体疑点交回给它；是否采纳由 brain 决定并留痕，
这样也能统计“Jev 提醒了多少次、brain 改了多少次、改了之后结果更好吗”。

## 8. 探索型的事：计划循环，不计划路径

产品、创意、研发这类事，目标本身要边做边弄清楚，人是共同创作者，推倒重来是正常进展。
用执行型的打法管它（排完整路线、按截止追进度）是错的。

| | 执行型（task） | 目标型（goal） | 探索型（explore） |
|---|---|---|---|
| 计划的是 | 路径 | 先判断可行性，再定路径 | 一轮一轮的循环：试 → 给委托人看 → 学到什么 → 继续 / 转向 / 停 / 收敛 |
| 委托人 | 确认计划 | 定约束、做决定 | 每轮看具体的东西、给方向 |
| 风险 | 赶不上截止 | 假设不成立 | 很久没对齐、超时间盒、原地打转、该收敛没收敛 |

实现：
- `kind=explore` 的计划起草即执行，修订不用重新确认；节点记着自己是第几轮试的；
- `plan learn` 记下每轮的结论和方向（continue / pivot / stop / converge），以及哪些问题有了答案；
- 上一轮的东西派出去之后，委托人再说话时，要先 learn 才能起草下一轮（防止只改计划、不留结论）；
- pivot / stop 自动停掉旧方向没做完的尝试；converge 把计划变成执行型草案，走正常的确认流程；
- 探索项目不报截止日期类风险，改报：`explore_unreviewed`（3 天没对齐）、`explore_timebox`（时间盒用了八成 / 已过）、`explore_converged`（问题都有答案了）；
- Jev 在 learn 时检查是否回到了放弃过的方向、是否和之前的结论矛盾但没说为什么。

## 9. Triage：分对类，后面才会越捋越顺

分类不是一个步骤，而是贯穿始终的一种动作：每一层都先回答“这是哪一类事”，再交给对应的机制。

| 层 | 分什么 | 谁来分 | 分完交给谁 |
|---|---|---|---|
| 消息进来 | 意图、对委托的回复是什么、急不急、规模（handoff / program / goal / explore / other）、是否明显做不到、是否一条消息里有好几件事 | Jev | 唤醒策略、自动登记、给 brain 的提示、委托前的规划闸门 |
| 一堆事 | 每件事放进哪个桶（交出去 / 规划 / 目标 / 探索 / 拍板 / 回答 / 记下 / 不做），急不急，要不要委托人参与 | `triage` 工具（Jev 分，代码分组排序） | brain 按桶处理：拍板的先列出来（会卡住别的），急的先办 |
| 找谁做 | agent 还是人；找人的理由（审批、决定、现实动作、关系、判断、知识、能力） | 代码规则 + Jev 语义匹配 | delegate / 计划节点 |
| 产出 | 探索性（调研、草稿）还是承诺性（改动、动作、决定） | brain 写在节点上，代码执行 | 探索性的马上做，承诺性的等确认 |
| 风险 | 现在 / 今天 / 留意 | 规则 + 打分 | 收件箱、唤醒 |
| 重新分类 | 交出去的事其实是个项目、探索收敛了、周期性工作该沉淀了 | brain（converge）、规则（routine） | 换机制，并告诉委托人 |

分工原则：
- **Jev** 做快而窄的分类，给概率；
- **代码**定义类别、按类别执行硬规则（闸门、自动派发、风险口径）；
- **brain** 处理分类拿不准的、分错了要改的，并对每一类做真正需要思考的部分。

分类拿不准时（置信度低），先想清楚它到底是什么，再动手。

## 10. 跟进不归 bot 执行的工作：原子能力，不对接具体系统

委托人的项目散在各处（项目文件夹、tracker、仓库、别的 agent 的会话），今天是 hp，明天可能是 Linear、
Claude Code projects、Cursor projects。bot 不对接其中任何一个，而是像一个新来的幕僚长那样跟进：

| 原子能力 | 工具 | 说明 |
|---|---|---|
| 看 | `look` | 读文件、列目录（带修改时间）、跑允许的只读命令（默认 git / gh 的读命令）、GET 允许的主机；只读、限根目录、截断、遮密钥 |
| 小抄 | `dossier` | 每个项目一份 bot 自己写的跟进手册：目标与完成条件、真相在哪和具体怎么看、谁在做、节奏、什么算进展和风险；每次处理这个项目时带上 |
| 盯 | `watch` | 定期看一个来源，代码比对；只在有变化（附差异）、连续看不了、超过预期时间没变化时产生 `observation` 信号（默认批量唤醒） |
| 放行 | `observe_allow` | 委托人允许新的只读命令模式（如 `hp * get`、`linear issue list`） |

具体系统只出现在数据里：小抄的文字、来源和盯点的探针参数。换系统时 bot 重新看、改小抄，核心代码不动。
推和记（`act` / `act_allow`）：
- 三种动作：跑命令（不经 shell）、写文件（追加或替换，只能在开放的根目录内，不穿过符号链接）、
  往现成的 agent 会话递话（怎么续会话由 `[observe.sessions]` 的命令模板决定，内置 claude 和 codex；异步，回复作为信号回来）。
- 每个动作都要委托人，而且确认和具体动作绑定（代码强制，不靠 prompt）：
  - 委托人的直接指令（“把 health 改成 on_track”）算同意这一个动作：他的每条消息最多确认执行一个动作；
  - 要做多件事、或做他没说清的事：先 `act kind=propose` 登记一个提案（每个动作原样记下），给委托人看，
    同意后 `kind=proposal id=… confirmed=true` 按原样执行，每个提案只执行一次；
  委托人说“以后可以直接做 X”时，用 `act_allow` 记下尽量窄的许可（如 `write ~/code/projects/*/handoffs/**`），太宽的许可会被拒。
- 每次动作都进审计（最近 300 条，项目小抄下面显示最近 5 条）。

造工具（`toolbox`）：
- bot 自己的工具箱：小脚本（sh / bash / python3），把反复要拼的看法或做法变成一次调用；一般由 agent 写，bot 登记。
- 审批绑在代码上：委托人批准的是某一版代码（内容哈希），代码一改就要重新批准；没批准的工具哪里都跑不了。
- 看类工具给 `look` / `watch` 用（`kind=tool`），盯一个工具就把“每天数一遍存量”变成一个只在变化时才叫醒 brain 的数字；
  做类工具走 `act`，照样要委托人同意或长期许可。
- 脚本写在 bot 数据目录的 `toolbox/` 下，按代码哈希命名；运行时和其他命令一样受根目录、超时、输出上限和遮密钥的约束。

评测：G33–G35 用三种不同格式的项目文件夹（hp 风格、纯 markdown、tracker 导出）测接管；
G36 测盯到变化后的判断；G37 测长期许可下写交接、且不越界；G38 测没说清时先列提案、同意后按提案执行；G39 测直接指令只改那一处；G40 测 agent 写的脚本进工具箱，委托人批准前不能用、批准后用来盯。`fixture` 指定项目文件夹，`write` 步骤模拟外部更新。

## 11. 定时唤醒

brain 答应“以后做”的事不能靠记性。`wakeup` 让 bot-connect 到点叫醒它：
- 一次性（`when`：周五 15:00 / 明天上午 / 2h，按人的说法解析）或周期性（`every`：cron、`@every 1d`、`@daily`，可加 `TZ=` 前缀）；
- 到点产生一个 `wakeup` 信号（默认立即唤醒），正文是 brain 当时给自己留的话，带项目和事项；周期唤醒自动排下一次；
- 用 bot 自己的时钟，评测里可用虚拟时间测；概览里显示接下来的几次唤醒；最多 50 个，周期最短 15 分钟（每次唤醒都花一轮额度）。

三者的分工：要**记得去做**一件事用 `wakeup`；要**知道某样东西变没变**用 `watch`（不花额度）；
旧的 `schedule_create` 只用于往别的会话定时投递指令。评测：G41（周五提醒 + 每周一周报）。

### 借鉴 multigent 的作息（heartbeat）

- **条件唤醒**（multigent 的 `wakeup_condition` / `wakeup_preset`）：唤醒可带一个探针（命令、文件、目录、工具箱里的工具），
  到点由代码先看，没结果就跳过这一次、不花 brain 额度；有结果就带进唤醒正文。
- **工作时段**（`active_hours` / `active_days`）：`[bot.wake] hours / days`。批量信号、例行、brain 的周期唤醒只在时段内发生，
  时段外到点的顺延到下一个时段开头；发给 bot 的消息、高风险、一次性的定时提醒不受限。
- **例行**（`interval` + `wakeup_prompt`）：`[[bot.routines]]`，委托人定的固定作息（如工作日早上过一遍所有项目），
  启动时同步成唤醒（`RT-<name>`），brain 取消不了；配置里删掉就结束。
- **唤醒统计和每日预算**（`wakeup_count_today`）：记录每天唤醒次数，概览里显示；`daily_budget` 用完后非紧急的唤醒等到第二天，
  防止盯点或例行把额度烧光、让线上 bot 停摆。
- 已有、无需借鉴的：按来源决定马上 / 批量 / 忽略（对应 `triggers` + `trigger_debounce`），醒来先跨项目分类，一个主会话，错过的周期只补最新一次。
