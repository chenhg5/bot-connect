# Brain 的决策能力：怎么来，怎么评

> 用词：bot（brain）是 principal，负责推动一切；给它目标的人叫**委托人**（principal）。

> 结论先行：不训练模型。决策能力由三样东西组合出来：
> **(1) 规划协议**（skill + prompt，告诉它“好的 PM 怎么想”），
> **(2) 计划是一等数据**（工具强制结构：分解、依赖、并行、谁做、为什么是这个人），
> **(3) 委托人的风格配置**（风险偏好、预算、要不要先问）。
> 评估用 golden case + Jev 打分 rubric，以及上线后的结果指标。

## 1. 用两个真实问题检验当前设计

### 例 A：「帮我给我的开源项目搭建一套完整的可行的周期发版策略」

bot 是这件事的 principal：它负责把事推到底，委托人只在需要他的地方出现。
它不自己读代码、写策略，第一反应是“拆成哪几块、每块让谁做”，而且这张图只是**草案**：

| 节点 | 做什么 | 谁 | 依赖 |
|---|---|---|---|
| R1 现状调研 | 读仓库：提交频率、tag 历史、CI、贡献者数、issue 节奏 | agent（研究型） | — |
| R2 同类调研 | 3–5 个同体量项目的发版策略（semver、train、LTS） | agent（研究型） | — |
| D1 方案草案 | 基于 R1+R2 出 2–3 个方案，每个写清代价 | agent | R1, R2 |
| C1 对齐 | 和委托人、核心维护者确认：节奏、谁来发、要不要 LTS | 人（decision） | D1 |
| …… | 落地节点在 C1 之后才定，不预先编 | 待定 | C1 |

要点：
- R1、R2 **并行**；只有 C1 需要人，且只问人能回答的那一步。
- **计划在确认前不是计划**。节点、执行者、时间都要和对应的人确认（他们接下 = 节点定下），
  确认后 bot 再展开落地部分。落地怎么做取决于选的方案，提前写成“合并某个 PR”是在替人做决定。
- 如果发版是周期性的，确认后的计划里应有一个复利节点：把发版做成可复用的 worker/skill。
- 当前设计能表达这些：Item + depends_on + needs(decision) + delegate。**缺的是**：计划的状态
  （草案 → 确认中 → 已定 → 执行中），以及 brain 不一定会这样想（会自己直接写策略）。

### 例 B：「在一年内帮助我赚到 100 万」

这是**目标**，不是任务。好的 PM 先做可行性，不先做承诺：

1. **澄清约束**（问委托人，一次问完）：起始资源（钱、时间、技能、已有产品/受众）、风险底线（能亏多少）、
   不做什么（法律、道德、时间边界）。这一步是 decision/knowledge，必须找人。
2. **并行调研**（全部派 agent）：3–5 条路径（产品化现有项目、咨询/服务、内容、投资…），
   每条给出：单位经济、到 100 万需要的量、前 3 个月的验证指标、主要风险。
3. **可行性门**：汇总成“哪条路径在约束下可能、概率大约多少、要先验证什么”。
   如果都不可行，**直接说不可行**，并给出可行的降级目标（例如“一年 30 万，路径 X”）。
4. **只为第一个验证周期建项目**（例如 6 周验证路径 X 的付费意愿），设里程碑和止损条件；
   一年目标挂在根上，每个周期复盘再决定下一个周期。

当前设计缺的东西：
- **目标（Goal）与项目的区别**：目标有可行性状态（未评估 / 可行 / 有条件可行 / 不可行）、
  假设、止损条件，下面挂多个验证周期（项目）。
- **调研节点的产出是“结论 + 证据 + 置信度”**，不是代码。
- **风险偏好决定路径选择**：同样的调研，谨慎的委托人选低方差路径，激进的委托人接受高方差。

## 2. 偏好不靠模型“性格”，靠委托人配置

风险偏好是**委托人的**，不是 bot 的。它应该是配置 + 可在对话里修改的 profile：

```toml
[principal.style]
risk = "cautious"          # cautious | balanced | bold
ask_before = ["spend>500", "public", "external_contact", "irreversible"]
budget_month = 2000        # 能花的钱（API、外包、服务）
parallel = 4               # 同时在跑的 agent 任务上限
explore_ratio = 0.2        # 多少精力给“复利投资”（工具、训练 worker）
```

用法分两层：
- **规则层（代码）**：ask_before、预算、并发上限是硬约束，authorize/delegate 里检查。
- **判断层（brain）**：risk 写进 briefing，比如“委托人偏谨慎：先验证再投入；优先低方差路径；
  不确定时先问”。brain 在给方案时必须说清每个方案的风险，然后按风格推荐。

## 3. 让 brain 有这种思路：harness，不是训练

模型本身已经会分解问题，缺的是**被逼着按 PM 的方式输出**。做法：

1. **plan 工具（结构强制）**：`plan_goal` / `plan_item` 一次提交一张图：节点、依赖、每个节点的执行者类型
   （agent/人）和 why、并行组、产出物、复利标记。代码校验：
   - 每个“找人”的节点必须有 why（已有）；
   - 有依赖环、无执行者、全部串行但其实可并行 → 拒绝并说明；
   - 研究/起草类节点指给人 → 提示“这类事 agent 能做”。
2. **规划 skill（思路模板）**：遇到新目标时加载，内容是 PM 的检查单：
   - 这是目标还是任务？目标先做可行性。
   - 我知道什么、不知道什么？不知道的 → 调研节点（派 agent）。
   - 哪些步骤彼此独立？→ 并行。
   - 哪一步真的需要人？只把那一步给人。
   - 这件事会重复吗？→ 加一个复利节点（工具 / skill / 专门的 worker）。
   - 最坏情况是什么，止损条件是什么？
3. **代码算能算的**：关键路径、最早完成时间、并行度、资源冲突，用已有的 Forecast/Graph 计算，
   回给 brain 作为 plan 工具的结果（“关键路径 R1→D1→H1→B1，预计 5 天；H1 是瓶颈，等你决定”）。
4. **Jev 做快判断**：新消息“是目标还是任务”“需要可行性评估吗”“这个节点 agent 能不能做”，
   用 noul/choice 先分好类，brain 只处理需要思考的部分。
5. **复利账本**：记录每类工作做了几次、每次耗时；重复 ≥3 次的工作类型自动成为信号
   （“发版做了 3 次，每次 2h，建议做成 worker”）。这是规则，代码就能算。

训练的位置：以后如果 golden case 的失败集中在“模型不会按协议想”，可以用积累的转录做偏好数据，
但这是最后一步，而且不在我们的范围（不碰 agent loop / 模型）。

## 4. 怎么评估决策能力

三层，和现有 eval 框架一致：

**(a) 结构检查（代码，确定性）**：对 plan 工具产出的图检查：
- 研究/起草节点是否都给了 agent；
- 人节点是否都只承担 why 范围内的那一步；
- 独立节点是否并行（关键路径长度 / 总工作量）；
- 目标是否先有可行性节点再有执行节点；
- 周期性工作是否有复利节点。

**(b) Rubric 评分（Jev score，对转录打分）**：每个规划 case 问 4–6 个窄问题，例如：
- “brain 是否先澄清了约束再开始执行？”
- “是否明确说出了不可行或有条件可行的部分？”
- “推荐是否符合委托人的风险偏好 `principal.style.risk`？”
- “有没有让人去做 agent 能做的事？”

**(c) 结果指标（上线后）**：计划被委托人原样接受的比例、计划变更次数、预测 vs 实际完成时间、
人被打扰次数 / 闭环交付数（北极星是每周闭环委托数）。

规划类 golden case（新增 G20+）：
- G20 开源发版策略：调研并行、决策给委托人、落地给 agent、有复利节点。
- G21 一年 100 万（谨慎）：先问约束，调研派 agent，给出可行性结论，不立刻建执行项目。
- G22 同上（激进）：同样流程，推荐路径方差更高，但仍有止损条件。
- G23 明显不可行的目标（“下周让项目 10 万 star”）：直接说不可行，给替代目标。
- G24 重复工作：第三次派同类活时，提出做成工具/worker。

## 5. 计划的生命周期：草案要和人对齐才算数

```
draft ──(拆完、代码校验通过)──▶ proposed ──(相关的人逐个确认)──▶ agreed ──▶ active ──▶ done
   ▲                                   │ 有人改时间/拒绝/提出别的方案
   └──────────────(修订)───────────────┘
```

- 节点的“确认”复用委托机制：给人的节点就是 offer，接下 = 确认，还价 = 修订输入。
- agreed 的条件由代码判断：所有人节点已接下、委托人对关键决策已答复、没有依赖环。
- 只有 agreed 的计划才进入风险检测（will_miss 等）；草案阶段不报延期。

## 6. Reflection：放在哪、谁来做

模型自己会反思，但它审自己的计划容易“自洽地错”。外部检查的价值在于**换一个角度、问具体的问题**。
不建议随机加检查点，建议按代价放：

| 时机 | 谁检查 | 检查什么 | 代价 |
|---|---|---|---|
| 每次提交计划 | 代码 | 依赖环、无执行者、可并行却串行、该给 agent 的给了人 | 0 |
| 计划从 draft → proposed | Jev（3–5 个窄问题，一次请求） | 先澄清了吗？有可行性判断吗？找人的理由成立吗？符合风险偏好吗？ | ~1s |
| 对外说“做不到 / 不可行” | Jev | 理由是否来自证据（调研结果、预测），而不是猜 | ~1s |
| Jev 低分 | brain 自己 | 把问题和分数回给 brain，让它改或说明为什么不改 | 一次 turn |
| 事后（离线） | Jev 抽样打分 | 随机抽取已完成的决策，按同一套 rubric 评分 | 不影响线上 |

随机抽样适合**评估**（离线统计决策质量，形成指标），不适合线上：线上检查应该放在代价大、
不可逆的决策点上。Jev 分数不直接否决 brain，只是把具体疑点交回给它；是否采纳由 brain 决定并留痕，
这样也能统计“Jev 提醒了多少次、brain 改了多少次、改了之后结果更好吗”。

## 7. 已实现（代码位置）

| 概念 | 代码 |
|---|---|
| 委托人（principal）与 bot 的 owner 意识 | `shared.Principal`、`RolePrincipal`；人设与协议在 `internal/brain/prompt.go` |
| 计划节点：执行者、为什么是人、产出、复利、周期性 | `planning.Node`（`internal/domain/planning/plan.go`） |
| 结构检查、并行批次、关键路径 | `planning.Analyze`：找人没理由、决定交给 agent、执行者不存在 → 拒绝；调研给了人、全串行、周期性工作没有复利节点 → 提醒 |
| 计划阶段：草案 → 待确认 → 执行中 → 完成，修订要重新确认 | `portfolio.Plan`（`internal/domain/portfolio/plan.go`） |
| 起草、提议、委托人同意、自动推进 | `app.DraftPlan / ProposePlan / AgreePlan / advancePlans`（`internal/app/plan.go`）：探索性节点（调研、起草）起草时就交给 agent；其余节点在全员确认后、依赖完成时自动派发，并带上前置节点的结果；并发受 `style.parallel` 限制 |
| 人确认自己的部分 | propose 时给每个有节点的人发一个 review 类请求（approve / change） |
| 草案阶段不报风险 | `attention.committed`：未确认计划里还没派出的节点不进风险检测 |
| 重复工作提醒 | `attention.Routine`：同一类工作完成 ≥3 次且没有复利节点 → 信号 |
| 委托人风格 | `[bot.style]`（risk / ask_before / budget_month / parallel），`app.Style.Describe()` 进简报 |
| Jev 审视计划 | `judge.PlanReview`：5 个窄问题（agent 优先、并行、可行性有依据、符合风险偏好、先对齐再投入），低分作为疑点回给 brain，不拦截 |
| 工具 | `plan`（draft / propose / agree / status），agree 只能在委托人说了话的回合里调用 |
| 评测 | `plan` / `no_plan` 检查；G20–G24 |
